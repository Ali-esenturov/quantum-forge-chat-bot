## Общая информация по базе знаний

В проекте используется **синтетическая база знаний** о вымышленной строительной компании **NordBuild Dynamics (NBD)**.  
Корпус создан специально для демонстрации корректной работы RAG-пайплайна и исключения влияния внешних знаний модели.

---

## Структура базы знаний

База состоит из **30 отдельных текстовых файлов** (1 файл = 1 логическая тема), сгруппированных в 6 доменных блоков:

- **Corporate & Governance (NBD-CORP-###)** — юридическая структура, руководство, совет директоров, организационная модель, стратегия  
- **Finance (NBD-FIN-###)** — годовая выручка, квартальная разбивка, доход по сегментам, расходы, активы  
- **Projects (NBD-PRJ-###)** — описание строительных проектов и модель жизненного цикла  
- **Compliance & Safety (NBD-COMP-###)** — стандарты безопасности, требования к подрядчикам, инциденты, аудит, экология  
- **Operations & Engineering (NBD-OPS-###)** — оборудование, техобслуживание, инженерные стандарты, закупки, контроль качества  
- **HR & Internal Policies (NBD-HR-###)** — роли сотрудников, компенсации, обучение, этика, план реагирования на ЧС  

---

## Формат документов

Структура файлов обеспечивает:
- чёткую тематическую сегментацию
- минимальное пересечение терминологии между документами
- улучшенное качество векторного поиска

---

## Canary-маркеры (проверка использования контекста)

Каждый документ содержит уникальный `CANARY`-маркер
В тестовом наборе есть специальные вопросы, требующие возврата конкретного CANARY-значения

Это позволяет доказать, что:
- при **RAG ON** модель использует retrieved-контекст
- при **RAG OFF** модель не способна "угадать" маркер

---

## Индексация в FAISS

Перед загрузкой в FAISS:

- Каждый файл разбивается на чанки фиксированного размера
- Каждый чанк сохраняется вместе с метаданными: doc_id, chunk_id, type, date, source_file
- В FAISS сохраняются только embedding-векторы
- Метаданные чанков хранятся отдельно (`nbd_meta.jsonl`) и используются на этапе retrieval

Retrieval-логика:
1. Вопрос - embedding
2. Поиск top-k ближайших чанков в FAISS
3. Формирование CONTEXT из найденных чанков
4. Генерация ответа строго на основе CONTEXT

---

## Почему используется синтетический корпус

- Исключается использование реальных персональных или коммерческих данных  
- Исключается влияние запомненных моделью фактов  
- Обеспечивается воспроизводимость тестирования  
- Позволяет детерминированно проверять RAG (factual / canary / NOT_FOUND сценарии)
